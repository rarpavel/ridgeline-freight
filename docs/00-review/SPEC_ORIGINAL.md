## Goal

Build, in 4–5 weeks, a public demo of a RAG assistant that answers questions about the internal documents of a fictional US logistics company, **Ridgeline Freight** (Chicago, Illinois). The whole product targets the US market: documents, UI and demo are in English, with precise source citations. The project goes into the portfolio as proof that the author can build production-grade AI solutions rather than a toy "chat with PDF".

What the demo must convincingly show a client:

- answers with a link to the document and clause, verifiable in one click;
- an honest "this is not in the documents" instead of hallucinations;
- role-based access control;
- measured accuracy on a test set, not "it seems to work";
- the ability to switch to a local model for private deployment.

## Functional requirements

The MVP consists of six features; the first three are required for launch, the rest are added in stages.

| # | Feature | Definition of done | Priority |
|---|---------|--------------------|----------|
| 1 | Chat with streaming answers | The answer starts appearing in under 3 s; conversation history within a session | MVP |
| 2 | Source citations | Every claim has a reference `[document, clause/page]`; clicking opens the document with the fragment highlighted | MVP |
| 3 | Refusal without a source | If there are no relevant fragments, or the score is below the threshold, the answer is "this is not in the documents" with no fabrication | MVP |
| 4 | Access roles | Roles `sales`, `hr`, `ops`, `admin`; the role filter is applied at the SQL query level, not in the prompt | Stage 3 |
| 5 | Quality evaluation page | Table of test questions, system answers, scores, aggregate metrics; one-click re-run (admin only) | Stage 4 |
| 6 | Model switch | Choice between a cloud API and a local model via an OpenAI-compatible endpoint (Ollama); configured via env | Stage 4 |

Additionally: UI, documents and test questions are in English; US formats: dates `MM/DD/YYYY`, amounts in USD, US addresses.

Out of scope for the MVP: user document upload, multi-tenancy, mobile app.

## Architecture and stack

One Next.js application and one Postgres: ingestion writes chunks into the database, and every query reads from it with a role filter, so no separate vector database is needed.

```
ingestion:  documents → parse → structural chunking → embeddings → Postgres (pgvector)
query:      question → hybrid search (vector + full-text, role filter in SQL) → RRF → threshold → LLM → cited answer
```

The LLM is called through an OpenAI-compatible client, so switching between the cloud and Ollama is only a change of `baseURL` and model name in env.

| Layer | Technology | Why |
|-------|------------|-----|
| UI + API | Next.js (App Router), TypeScript strict | One repository, the author's main stack |
| Database | Postgres + pgvector | Vectors and SQL access filters in one query |
| LLM client | npm `openai` with configurable `baseURL` | Same code for the cloud and Ollama |
| Embeddings | `text-embedding-3-small` or `bge-m3` via Ollama | `bge-m3` is multilingual and runs locally |
| Parsing | `mammoth` (DOCX), `pdf-parse`, `tesseract.js` (OCR) | Everything in Node, no Python service |
| Auth | Auth.js with demo accounts | Roles in the session, no own `users` table |

## Database schema

Five tables in one Postgres with the pgvector extension are enough; no separate vector database is needed. The dimension `vector(1536)` is for OpenAI `text-embedding-3-small`; if you choose a different embedding model, change it to match the model.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documents (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  title         text NOT NULL,
  doc_type      text NOT NULL,          -- contract | policy | sop | pricelist
  access_roles  text[] NOT NULL,        -- {'sales','admin'}
  source_path   text NOT NULL,          -- path to the original in storage
  checksum      text NOT NULL,          -- for incremental re-indexing
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE chunks (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  document_id   uuid NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  ordinal       int NOT NULL,           -- order within the document
  section_ref   text,                   -- 'Sec. 4.3', 'p. 2'
  content       text NOT NULL,
  token_count   int NOT NULL,
  embedding     vector(1536) NOT NULL,
  tsv           tsvector GENERATED ALWAYS AS (to_tsvector('english', content)) STORED
);

CREATE INDEX chunks_embedding_idx ON chunks USING hnsw (embedding vector_cosine_ops);
CREATE INDEX chunks_tsv_idx       ON chunks USING gin (tsv);
CREATE INDEX chunks_document_idx  ON chunks (document_id);

CREATE TABLE eval_questions (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  question        text NOT NULL,
  expected_answer text,                 -- NULL = the answer is not in the documents
  expected_doc_id uuid REFERENCES documents(id),
  role            text NOT NULL
);

CREATE TABLE eval_runs (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  model       text NOT NULL,
  started_at  timestamptz NOT NULL DEFAULT now(),
  metrics     jsonb                     -- aggregated run metrics
);

CREATE TABLE eval_results (
  run_id        uuid NOT NULL REFERENCES eval_runs(id) ON DELETE CASCADE,
  question_id   uuid NOT NULL REFERENCES eval_questions(id) ON DELETE CASCADE,
  answer        text NOT NULL,
  cited_chunks  uuid[] NOT NULL,
  scores        jsonb NOT NULL,         -- correctness, faithfulness, retrieval_hit
  latency_ms    int NOT NULL,
  PRIMARY KEY (run_id, question_id)
);
```

The `'english'` configuration for `tsvector` gives stemming of English words (penalty → penalties, ship → shipping), which noticeably improves the full-text part of hybrid search.

Users and roles for the demo can be hard-coded (4 demo accounts) or taken from the auth provider; a separate `users` table is not needed in the MVP.

## Ingestion and retrieval pipeline

Answer quality is determined by retrieval, not by the model, so most of the time should be invested here.

**Ingestion** (CLI script `pnpm ingest`, run manually):

1. Parsing: DOCX and text PDFs directly; scans via OCR; rate-sheet tables stored as Markdown tables so the model sees rows and columns.
2. Chunking by document structure: split by headings and clauses ("Section 4.3. Late Delivery Penalties"), not by a fixed number of characters. Target size ~300–600 tokens, overlap ~50.
3. Each chunk gets a context prefix: document title + section. This noticeably improves retrieval for short clauses.
4. Embeddings in batches, written to `chunks`; documents with an unchanged `checksum` are skipped.

**Query handling:**

1. Hybrid search: top-20 by vector + top-20 by `tsv`, with the filter `access_roles && $userRoles` in the same SQL.
2. Merge results via Reciprocal Rank Fusion.
3. Cut off by a relevance threshold; if nothing remains, answer "this is not in the documents" without calling the LLM.
4. The top-5 chunks go into the prompt with ids; the model must reference ids in the format `[c:<id>]`.
5. Post-processing: id references are turned into clickable citations; references to ids that were not in the context are dropped and logged.

Optional in Stage 4: a reranker (cross-encoder) between steps 2 and 3 — improves precision but adds latency.

## Data generation

About 45 documents in English in the style of a real US logistics company are needed: amounts in USD, dates `MM/DD/YYYY`, US addresses, Illinois governing law in contracts. The key is to first generate a **fact registry**, and then documents from it. This gives a ground truth for tests and no contradictions between documents.

| Type | Count | Access roles | Format |
|------|-------|--------------|--------|
| Customer Service Agreements (MSA) | 15 | sales, admin | DOCX, 3 of them as scanned PDFs |
| Carrier & Subcontractor Agreements | 8 | ops, admin | DOCX |
| Employee Handbook policies (PTO, travel, remote work) | 8 | hr, admin | DOCX |
| Warehouse & Delivery SOPs | 10 | ops, admin | DOCX |
| Rate Sheets (freight rates, accessorial fees) | 4 | sales, admin | PDF with tables |

**Step 1 — fact registry** (JSON, stored in the repository):

```
Generate a JSON array of fictional facts for "Ridgeline Freight", a mid-size
US logistics company headquartered in Chicago, Illinois.
For each document in the list below, produce 5–8 facts.
Fact: { "doc_slug", "fact_id", "statement", "value" }.
Requirements:
- concrete numbers, dates (MM/DD/YYYY), amounts in USD, terms in days (e.g. Net 30);
- at least 10 facts that differ between similar agreements
  (different late-delivery penalties, payment terms, liability caps);
- 5 exception facts ("except for hazmat shipments");
- realistic US context: Illinois governing law, PTO accrual, at-will employment,
  accessorial fees, detention charges;
- no real companies, people, addresses or phone numbers.
Document list: <list from the table above>
```

**Step 2 — document from facts:**

```
Write the full text of "<title>" for Ridgeline Freight in US business English.
Type: <type>. Length: 2–4 pages, numbered sections (1., 1.1., …).
Include ALL facts below, faithful in meaning, spread across different sections
rather than grouped in one place. Add typical boilerplate (definitions,
force majeure, governing law, notices) so the facts are not on the surface.
Do not add any numbers, dates or amounts that are not in the facts.
Facts: <JSON facts for this document>
```

**Step 3 — processing:** convert Markdown → DOCX via pandoc; render 3 contracts as image PDFs to imitate scans; verify with a script that every `value` from the registry is actually present in the document text.

## Quality evaluation

Test set: 60 questions generated from the fact registry, plus a manual check of each. Question distribution:

| Question type | Count | What it checks |
|---------------|-------|----------------|
| Direct fact | 25 | Basic retrieval and citation |
| Comparison of two documents | 10 | Retrieval of several chunks from different documents |
| Exception / condition | 8 | Whether the model loses qualifiers |
| No answer | 10 | Honest refusal without fabrication |
| Other role | 7 | That the access filter does not leak data |

Metrics:

- **Retrieval hit rate** — share of questions where the required document is in the top-5. Computed deterministically, without an LLM.
- **Correctness** — the answer matches the reference; scored by an LLM judge with a 0/1 rubric and an explanation.
- **Faithfulness** — all claims are supported by the cited chunks.
- **Refusal accuracy** — share of correct refusals among no-answer and other-role questions.
- **Latency p50 / p95** — time to first token and to the end of the answer.

Portfolio targets: hit rate ≥ 90%, correctness ≥ 85%, refusal accuracy ≥ 95%, zero cross-role leaks. Show the real numbers honestly even if they are slightly lower — clients trust numbers more than a perfect 100%.

Run: `pnpm eval --model <name>` writes the run into `eval_runs`; the `/admin/eval` page shows the latest run and a model comparison.

## Deployment, security, budget

The simplest option is Vercel for Next.js and a managed Postgres with pgvector (Supabase or Neon, region `us-east` — closer to US users); both have free tiers that are usually enough for a demo. Alternative: a single VPS with Docker Compose (app + Postgres) if you want to show DevOps skills.

Mandatory for a public demo:

- Rate limit per IP and per account (e.g. 20 requests per hour) — otherwise a bot will burn the API budget.
- A hard monthly spend limit in the LLM provider's dashboard.
- API keys only in server env; no LLM calls from the browser.
- Limits on question length and number of messages per session.
- Demo access behind login (4 role accounts), not an open chat.

Budget: on demo traffic the main costs are the LLM API and one-off indexing; with a cheap model and limits this is usually single-digit dollars per month. Check exact prices on the providers' pages before launch — they change often.

The local model (Ollama) is not used in the public deployment: the switch is shown in the video and works when run locally.
